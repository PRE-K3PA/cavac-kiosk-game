# Team 작업 규칙

`AGENTS.md` 가 이 파일보다 우선합니다. 담당 영역은 `TEAM_OWNERSHIP.md` 가 원본입니다.

이 규칙은 Team 워크플로우(`/start-task`, `/implement-screen`, `/implement-component`,
`/fix-issue`, `/finish-task`)로 작업할 때 적용합니다. 단독 작업은 `AGENTS.md` 의 작업 방식을 따릅니다.

## Team Lead 는 메인 세션입니다

서브에이전트는 다른 서브에이전트를 호출할 수 없습니다. 그래서 Team Lead 역할은 메인 세션이 맡고,
아래 에이전트를 직접 호출합니다.

| 에이전트 | 역할 |
| --- | --- |
| `implementer` | 담당자 한 명의 범위로 구현 (Worker) |
| `reviewer` | 규칙, 소유권, 아키텍처, 일관성 리뷰 |
| `simplifier` | 동작을 바꾸지 않는 범위의 단순화 |
| `verifier` | 최종 검증 |

Team Lead 는 명시적으로 구현을 배정받은 경우를 제외하고 기능 코드를 직접 구현하지 않습니다.
Team Lead 는 작업을 조정할 뿐, 기존 프로젝트의 담당 구조를 대신하지 않습니다.

## 승인

- 사용자가 승인한 작업 범위 안에서는 Team Lead 가 내부 작업 분할과 파일 범위를 결정합니다
- Worker 는 허용된 파일 범위 안에서 사용자 승인을 따로 요청하지 않습니다
- 최초 요청 범위를 벗어나는 작업은 Team Lead 도 사용자 승인 없이 진행하지 않습니다
- `TEAM_OWNERSHIP.md` 에서 `(확인 필요)` 또는 담당자 `없음` 인 경로는 수정 전에 사용자에게 확인합니다

## 구현 전

1. `AGENTS.md` 와 `TEAM_OWNERSHIP.md` 를 읽습니다
2. 요청된 작업을 이해합니다
3. 관련된 기존 구현, 유사한 화면과 컴포넌트를 확인합니다
4. 재사용 가능한 컴포넌트, 훅, 스토어, 유틸리티, 타입을 확인합니다
5. `TEAM_OWNERSHIP.md` 의 경로별 담당자 표로 책임자를 결정합니다
6. 담당자 간 의존성과 공용 파일을 확인합니다
7. 의존성을 고려한 실행 계획을 세웁니다

## 담당자 배정

편의에 따라 작업을 배정하지 않습니다. `TEAM_OWNERSHIP.md` 를 기준으로 담당 Worker 를 결정합니다.

여러 담당자가 참여하는 영역에서는:

1. 실제로 수정되는 파일을 확인합니다
2. 파일 하나에는 활성 담당자 한 명만 배정합니다. 해당 파일의 책임(Main responsibility)에
   더 직접 해당하는 담당자를 고릅니다. 판단이 어려우면 사용자에게 확인합니다
3. Worker 간 의존 관계를 기록합니다

## 병렬 작업

수정 가능한 파일 범위가 서로 겹치지 않을 때만 병렬로 실행합니다.
병렬 Worker 를 실행하기 전에 각 Worker 의 수정 가능 경로를 나란히 적어 겹치지 않는지 확인합니다.

좋은 예: Worker A 는 백신 게임 화면 파일, Worker B 는 카드 게임 화면 파일

나쁜 예: Worker A 와 B 가 같은 공용 `Button` 을 수정, Worker C 가 별도의 `Button` 을 새로 생성

선행 의존이 있는 작업은 순서대로 실행합니다. 예: Electron API 추가(김나연) → 그 API 를 쓰는 화면.

## Worker 작업 지시

`implementer` 를 호출할 때 다음을 모두 프롬프트에 넣습니다. 서브에이전트는 대화 맥락을 모릅니다.

- 이슈 번호와 작업 목표
- 담당자 이름과 담당 영역
- 수정 가능한 파일/디렉터리
- 수정 금지 파일/디렉터리
- 완료 기준
- 관련 기존 구현과 재사용할 컴포넌트
- 다른 Worker 와의 의존 관계
- 필요한 검증 항목

## 의존성 분류

의존성은 파일 종류가 아니라 **현재 작업의 기능 완료를 막는지**로 판단합니다.

### 강한 의존성

다른 담당자의 변경이 끝나지 않으면 현재 작업의 기능 구현이나 검증을 완료할 수 없는 경우입니다.
기능 로직, 상태 관리, 데이터 구조와 타입, 컴포넌트 인터페이스, API / IPC / 라우팅, 공용 로직이
주로 해당합니다.

1. Worker 는 해당 영역을 수정하지 않고 Team Lead 에게 보고합니다
2. Team Lead 는 `TEAM_OWNERSHIP.md` 에서 담당자를 찾아 그 담당자의 Worker 에게 작업을 배정합니다
3. 의존 작업이 끝난 뒤 원래 작업을 이어갑니다

### 약한 의존성

다른 담당자의 변경 없이도 현재 기능을 구현하고 검증할 수 있고, 통합 단계에서 반영해도 되는
경우입니다. 스타일, 레이아웃, 문구, 이미지와 아이콘, 시각적 반응형 보정이 주로 해당합니다.

1. Worker 는 자기 담당 범위의 작업을 멈추지 않고 계속합니다
2. 다른 담당자 영역의 변경은 Team Lead 에게 공유만 하고 직접 수정하지 않습니다
3. Team Lead 가 해당 담당자에게 배정하거나, 사용자 승인 후 수정을 허용합니다
4. 최종 보고에서 반영 여부를 확인합니다

스타일이나 UI 변경이라도 사용자 입력, 화면 접근, 기능 동작, 검증 결과에 직접 영향을 주면
강한 의존성으로 처리합니다.

## 공용 코드

공용 컴포넌트, 훅, 유틸리티, 스토어, 타입, 스키마를 새로 만들기 전에 저장소 전체를 검색합니다.
우선순위는 재사용 > 확장 > 리팩터링 > 신규 생성입니다.
공용 코드를 기능 폴더 안에 따로 복제하지 않습니다. 공용 코드의 담당도 `TEAM_OWNERSHIP.md` 를 따르며,
새 Common 컴포넌트는 Common 담당자의 Worker 가 만듭니다.

## 구현 후

1. `reviewer` 를 실행합니다
2. `BLOCKER` 또는 `REQUIRED` 가 있으면 해당 파일 담당자의 Worker 에게 돌려보내 수정한 뒤
   `reviewer` 를 다시 실행합니다
3. 필수 항목이 해결되면 `simplifier` 를 실행합니다
4. 마지막에 `verifier` 를 실행합니다. 하나라도 `FAIL` 이면 완료가 아닙니다

## 최종 보고

- 담당자별 작업 결과
- 변경 파일
- 재사용한 기존 코드
- 새로 생성한 코드
- cross-owner dependency
- review 결과
- verifier 결과
- 사람이 최종 확인해야 할 사항
